# Mobile remote: trust model and threat model (Phases 1–3)

Scope: the remote gateway (crate `rift-remote`, run by `rift-terminal
remote`), the Rift windows that answer it, and the companion app
(`mobile/`), as specified in [remote-protocol.md](remote-protocol.md),
including the Phase 2 relay that carries connections from outside the local
network.

## Trust model

- **The desktop user** owns the shells. The gateway runs as that user and
  reads and drives Rift windows only through their control sockets, which
  refuse other uids.
- **Remote access is off by default.** `remote_access = true` (Settings ›
  Remote access) starts the gateway; turning it off stops it within 2
  seconds. A chip in every window's tab bar shows while a device is
  connected.
- **A device is trusted after pairing.** Pairing needs the QR code or link
  shown on the desktop: physical access, or the user passing it on. The
  secret in it works once, for 2 minutes. The device then has its own key;
  the desktop lists every paired device and revokes any of them.
- **The gateway is authenticated by its key,** which the device learned from
  the pairing link and pins. A machine that answers on the gateway's address
  without that key cannot complete the handshake.
- **The network is not trusted.** Every byte after the handshake is
  encrypted and authenticated (Noise XX, X25519, ChaCha20-Poly1305,
  BLAKE2s), in both directions.
- **The relay is not trusted.** It splices sockets and forwards Noise
  ciphertext; it holds no key and cannot complete a handshake as either side.
  Whoever runs it learns metadata only (below).

## Assets

| Asset | Why it matters |
|---|---|
| Terminal output | May contain secrets, tokens, customer data printed by programs |
| What a pane is asking, and the answer | A coding agent's permission ("make this edit?", "run this command?") is consent to code running; a password typed into `sudo` / `ssh` is a credential |
| Commands and working directories | Reveal projects, hosts and habits |
| The ability to type into a shell | Equivalent to running code as the user |
| Device private keys (phone) and the gateway key (desktop) | Impersonation of either side |
| Pairing secrets | Admit a new device for 2 minutes |

## Threats and answers

| Threat | Answer | Left for later |
|---|---|---|
| Someone on the network connects | Only paired device keys or a live pairing secret complete a session; failed handshakes are limited per address | — |
| Someone on the network reads or changes traffic | Noise XX: encrypted and authenticated; a changed byte ends the connection | — |
| A fake gateway on the network (or a replaced address) | The device pins the gateway key from pairing; the handshake aborts on any other key before the device sends its hello. A LAN address that answers with another key (an impostor, or another network reusing the address) is skipped and the next path tried, the relay last; the host shows "key mismatch" and stops only when the relay, or every path of a round, answered with another key. A network change tries such a host again; an impostor can deny service, never read or impersonate | — |
| A pairing link is seen by someone else | One use, 2 minutes; the desktop lists the device it created, which can be revoked | Showing the pairing device on the desktop for approval |
| A device runs something unexpected | `operate` devices only; `view` devices cannot run, send keys or type. A command runs only at a prompt, as one line without control characters, and becomes a visible block; the desktop shows a toast naming the device. The app shows the command first only with "Ask before running" on (off by default since the redesign: Run sends at once, as typing the command on the desktop would); the block it becomes and the desktop's toast are the record. Face ID / fingerprint before Run needs the app lock and "Ask before running" on (plus "Run with Face ID", on by default); then the keys that submit a line at a prompt (`enter`, `ctrl+m`, `ctrl+j`) ask too. Other keys (`ctrl+c`, arrows, `esc`, `tab`, other `ctrl+` letters) are sent without asking: they cannot submit a new command line by themselves. Typed text (the Terminal view) reaches only a program that is running, never a pane at its prompt or one whose submitted command the shell has not started yet; at a prompt keys never put text on the command line (no typing, history recall, history search, completion or ghost suggestion), and a submit key there while the line holds the desktop user's draft is refused `busy`, so a command line always arrives through the confirmed `run`. Two exceptions take typed text because the gateway cannot tell their prompt from a program: a shell without Rift's shell integration, and a prompt drawn on the alternate screen (tmux, screen, an ssh session running one); there text, like keys, can reach a shell's line (still `operate` only, toasted, and behind the Terminal view's authentication); the desktop's toast names the device but never shows the text (it may be a password). In the Terminal view one authentication holds until the view closes or the app leaves the foreground | — |
| Answering prompts from the phone (feature `waiting`) | Answering is the same input as typing: `operate` devices only (a `view` device sees the question and gets no answers), sent as `text` / `keys` through the same paths, limits and desktop toasts ("<device> typed into a program", never the text). A choice goes only to the question it was shown for: the app sends nothing when the pane's current question differs (another prompt, other entries), and a numbered entry is one digit, so an answer that arrives late lands in a program that is asking again only if it asks the very same question. No confirmation unless "Ask before running" is on (then Face ID first), as for Run; an agent's "Yes" is equivalent to the desktop user pressing it. Menus are read only while the pane runs a coding agent (Claude Code, Codex: the running block's command or the foreground job's name), so another program printing a menu-shaped screen never takes a phone's digit or arrows; a password prompt is any program's. What the phone is shown is screen text: the question, the menu's entries and up to 12 lines above it (the agent's diff or command), within the topology's bounds (300 / 9 × 200 / 12 × 200 characters); it never includes anything for a password prompt | A desktop setting to turn the `waiting` feature off separately from operate access |
| A password typed on the phone leaks | It goes once as an encrypted `text` message to the pane's program and is kept nowhere: not in the app's state, drafts, logs or keychain (`test/fleet.test.ts`), not in the desktop's toast, block history or transcripts (echo is off while it is read); the field is a secure text entry (no autocorrect, no screenshots of its content in the iOS switcher with the app lock's cover). A program that lies about echo (shows "password:" with echo on) gets the text like any typed line | — |
| A program fakes a menu or a password prompt to phish the phone user | The phone shows what the screen says, under the pane's place ("claude is asking · studio-mac · rift · pane 2"); a program that prints a fake question reaches only someone who answers it, and an answer is only input to that same program, which could read the same keys from the desktop user. A fake password prompt is the real risk: the phone says a password is typed into "<program> on <computer>"; the password prompt check also takes "the terminal reads without echo", which a hostile program can do too | Show the foreground process's path for password prompts |
| Lock-screen answers | "Needs you" alerts carry the program, the computer's name and the question (not the context lines). Their Yes / No need the phone unlocked (iOS `isAuthenticationRequired`), open the app and go through the same checks as an answer in the app; with "Ask before running" on the app asks for Face ID again first. Alerts are posted by the app on the phone (never through a push provider), so the question is never sent to Expo, Apple or ntfy | — |
| A device opens shells on the desktop | `open` (feature `open`) makes a new tab or split with the user's own shell, starting in the pane's folder; it runs nothing by itself. `operate` devices only (a `view` device gets `forbidden`), only while `remote_access` is on, at most 2 per second per connection; the desktop shows the new tab or pane and a toast naming the device | — |
| A device closes shells | `close` (feature `close`) ends a pane or a whole tab, without the desktop's running-command confirmation (the phone asks its user first). Same gates as `open`: `operate` devices only, only while `remote_access` is on, 2 per second per connection together with `open`; the desktop shows a toast naming the device. It can end a program the desktop user is running | Leave a device on `view`; revoke lost phones |
| A device starts shells while Rift is closed | `start` (feature `start`) exists only while the computer's user turned on `remote_when_closed` (off by default; the welcome lists `start` only then, and the gateway checks the setting again on every request). `operate` devices only, the `open` rate, at most 8 such shells; the phone asks for Face ID or the passcode first. Nobody watches the computer's screen, so it posts a notification naming the device, and the shells become ordinary tabs the next time Rift opens. Revoking the device or turning the setting off stops new ones; running ones stay until closed | Leave the setting off; revoke lost phones |
| Completion requests reveal files | `complete` returns what the desktop's own command line would complete: commands, options, paths under the pane's folder (and any path typed), git branches and the pane's and the imported shell history, at most 50 entries of 1 KiB each, at `output`'s rate; `operate` devices only (a `view` device gets `forbidden`): shell history can hold secrets typed on a command line, and path completion lists any folder | A setting to keep shell history out of `complete` |
| Chip menus reveal files | `dirs`, `branches` and `changes` list names only (sub-folders of the pane's folder, local branches, changed paths with status and line counts, untracked files included); `diff` returns one changed file's lines, its path matched literally, at most 2,000 lines / 256 KiB. `view` devices may read the lists and tracked files' diffs (what `git diff` in the pane would show); an untracked file's diff is its whole content (a `.env`, a key) and needs `operate`. The window answers them off its UI thread, so a large repository cannot freeze the desktop | — |
| A lost or stolen phone | Revoke it on the desktop: its connections close within a second and its key is refused; with the app lock on, nothing shows without Face ID / fingerprint or the device passcode | — |
| A device floods the desktop | Message size, `run`, `keys` / `text` and `output` rates, connection count, handshake deadline and idle limits; screens are capped at 300 × 120 and one per 100 ms, a cell at 16 combining marks and a screen message at 1 MiB; a phone that reads slowly holds at most one pending screen at the gateway (the newest, diffed against what it was sent), never a backlog; the window builds a screen only when the pane's output moved since the gateway's last read | — |
| A program in a pane injects protocol data | Output and screen text travel as JSON string content; nothing in them is interpreted, and screen colours are resolved on the desktop to `rrggbb` values the app checks | — |
| Another local user drives the gateway | Files under `remote/` are 0600 in a 0700 directory; control sockets check the peer uid | — |
| Notification content leaks to a push provider | Alerts while the app is closed go through Expo and Apple's / Google's push service only for a device that sent a push token. They carry the computer's name, the exit status, the gateway key and pane number, and the command line only when the user turned on "Show command in notification"; never output. A token the service no longer knows is dropped | — |
| Alerts through ntfy are read by someone else | Only for a device that turned on "Alerts through ntfy". The topic is the only secret: anyone who knows the topic name can subscribe and read the alerts, so the app makes it `rift-` and 128 random bits (22 base64url characters) and shows it only in Settings; turning the switch off keeps it (the computers stop posting to it), and turning it on again reuses it; "New topic" makes a new one (computers offline at the time may post to the old one until they reconnect). The ntfy server (ntfy.sh, or the user's own) sees each alert's title (the computer's name and exit status), its body ("Exit N" or "Finished", or the command line only with "Show command in notification"), the gateway public key and pane number in the `Click` link, and the computer's IP address; never output. The gateway posts only to `https://` topic URLs it validated (no user, query or fragment; at most 200 characters), with fixed headers and a body it builds itself, and never reads or logs the reply. Request forgery: it refuses the names `localhost` and `*.localhost` and IPv4 addresses that are loopback (127/8), unspecified (0/8), link-local (169.254/16, cloud metadata), broadcast or multicast (224/4), and a numeric host in any spelling but a plain dotted quad (`127.1`, `2130706433`, `0x7f.0.0.1`); IPv6 literals are refused. Still allowed: private LAN and 100.64/10 addresses (a self-hosted ntfy, Tailscale), and any DNS name, even one that resolves to an internal or loopback address; so a paired device, even `view`, can make the gateway send these fixed alert posts to an internal https service it names | Self-host ntfy with access control (ntfy users and tokens) |
| The gateway key file is copied | Same-user access already reads everything the gateway can | Hardware-backed key storage |
| The relay operator (or someone who took over the relay) reads traffic | Only Noise ciphertext crosses it; the phone pins the gateway key, so a relay that answers itself fails the handshake, and the host stops with "key mismatch" (the relay routes by the pinned key, so it is not retried past) | — |
| The relay learns who talks when | Routing ids (a hash of the gateway key), connection times, addresses and byte counts are visible to it — by default to the Rift maintainer, who runs the public relay `rift-relay.playhaws.com` | Self-host the relay (`packaging/relay.Dockerfile`) |
| Cloudflare tunnel: Cloudflare carries the tunnel | Cloudflare terminates TLS for the `trycloudflare.com` name and forwards the WebSocket to the relay on this computer; it sees what a relay sees (routing ids, timing, addresses, sizes) and the Noise ciphertext, never content or keys. The relay listens on loopback only and trusts `X-Forwarded-For` (Cloudflare appends the phone's address) for its rate limits. Anyone can reach the public name, but only this computer's gateway may register there (the relay refuses every other routing id, after its key proof), so it is no open relay for strangers' gateways | Self-host the relay (`packaging/relay.Dockerfile`) |
| Someone takes over a gateway's routing id at the relay | A registration must name the gateway's public key and prove it holds the private key (a Noise NK handshake from the relay); without the key nobody can claim the id, before or after a relay restart | — |
| The relay is flooded | Per-id pair limit, per-address connect rate and socket count (IPv6 per /64), a 10 s total deadline for each upgrade and registration, frame size, idle and accept deadlines; the id cap forgets the longest-offline id first | — |
| Someone who knows a routing id floods the gateway through the relay | Relay sockets have their own budget at the gateway, so LAN phones are never refused; relay phones can be slowed within the relay's per-address limits (a per-id cap would let the same person lock them out entirely) | — |
| A phone is picked up unlocked | Optional Face ID / fingerprint lock on launch and after 5 minutes in the background, and before running commands (conditions above); the app switcher shows a privacy cover, and on Android the window is marked secure (FLAG_SECURE) while the lock is on, so the Recents thumbnail, taken before the cover can draw, is blank and screenshots are blocked. A device with no passcode or secure lock screen cannot check anything, so the lock lets the owner in there | — |
| A device should keep watching but stop typing | Its permission can be lowered to `view` on the desktop; its connections close within a second and reconnect with the new permission | — |
| Unnoticed access | Every connection and failed handshake is recorded in the connection history the desktop shows; failed handshakes are dropped first when it is full, so a flood of them never hides a paired device's connections | — |
